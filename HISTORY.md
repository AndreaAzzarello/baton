# Development history

A short diary of the work on Baton, newest first. For what changed for users see [CHANGELOG.md](CHANGELOG.md).

## 2026-11-17
- 1.4.2 in progress (MCP server). Protocol 5 (`probe`, `capabilities`, the list in pages, MCP budget of 120 requests a minute); a connection that closes after a message was sent is no longer sent again; Baton is started without inheriting the output of `batonctl`; every refusal of the pipe carries a stable `ReplyCode` (`ChannelReply.Code`) and the API status and the activity log's reasons follow the code, not the words of the error (API 1.4.1 and `--json` unchanged, test on the fields: `LocalApiTests.Compatibility_ErrorsAndFields_AreThoseOf141`).
- `batonctl mcp` (`src/Baton.Cli/Mcp`): official SDK core package (2.3.1) with low-level handlers and hand-written schemas, 11 tools filtered by the level the app reports, explicit ids only (no "all"), at most 50 items per call, 2 calls in flight, timeouts, a 60-second budget for `add_downloads`, log on standard error, clean stop when standard input closes; the trimmed `batonctl.exe` is 15.5 MB with no trim warnings. `AgentText` (`src/Baton.Protocol`) removes control, bidirectional, zero-width, tag and variant-selector characters and cuts without splitting a surrogate pair. MCP calls, refused ones too, go to the activity log (`mcp.*`).
- Settings > Automation has an "AI agents (MCP)" and a "Local API" section; "Copy the MCP configuration" copies the JSON with the real path of `batonctl.exe`. `docs/MCP.md`, changelog, roadmap and READMEs describe it; the app, `batonctl` and the extension are 1.4.2.
- Review corrections, second round: agents may leave at most 1000 downloads waiting; refusals without the API token are counted in one line a minute; names, errors and paths from the API and `batonctl` lose hidden characters (and file names lose more of them); the API adds `displayUrl` next to `url`; the native host answers "busy" instead of starting a running app again; `batonctl probe` against Baton 1.4.1 says `appTooOld`.
- Review corrections, third round (command line): `--category` also finds a category by the name the interface shows; `--json` is read before the arguments are checked, so errors and `--help` answer as JSON; an exception is exit code 3 or 1, never a crash; `add` keeps what it already added when Baton disappears midway (`notAttempted` for the rest); a BOM on standard input is ignored and the console is set to UTF-8; `--folder` with a quote or forbidden characters is refused with the trailing-backslash hint; "Starting Baton..." goes to standard error and "could not start", "started but silent" and "busy" are told apart; `batonctl queues` and `batonctl categories` list the names to use; `docs/CLI.md` lists the JSON fields of every command (checked against the real output by a test) and says what `remove` does to files.
- The site menu of the extension follows "When to intercept"; a test of the MCP host no longer assumes the order of the answers.
- Real trials of 1.4.2 with an isolated app (SDK client, `claude -p`, read-only level, an agent-started queue, the pipe ACL, an app started as administrator, `chcp 850`): four corrections came out of them. An app started as administrator is reported as such by `batonctl` (exit 3) and MCP (`appElevated`) instead of a .NET resource key; the refusals that come from the app are worded in Italian from their code; the end-of-queue window of an agent-started queue is titled "Queue finished"; `tools/trials/ui.ps1` takes `-ProcessId` and refuses to act when several Baton processes run. Not verified: a remote client, the token in Win+V history, the browser against an elevated app. Next: the stop before the push.
- Final review of 1.4.2 (code and security, before the tag). No security finding at high confidence. Fixed, each with a test shown red then green: the activity log kept `user:password@` when the path or query of an address held an `@` (`AutomationLog.Clean`); the second start of Baton, the notification buttons and the native host threw when the app closed the connection without answering or ran as administrator (`LinkLauncher.TryActivateAsync`, `LinkOutcome.NoAnswer`, `NativeHost.ForwardAsync`, `Strings.ErrorAppElevated`); a refusal code unknown to this version is read as `Failed` instead of a broken connection (`ReplyCodeConverter`); MCP can no longer flood the activity log (refusals counted once per reason a minute, reads that worked not written). The elevated-app case (A24) was seen again at runtime with the final build: `batonctl` exit 3 in Italian, `appElevated` with `--json` and in MCP, registry unchanged. Known limit, for 1.4.3: the rule "Rename" does not apply to browser downloads that already carry a name.
- Release 1.4.2: tag `v1.4.2` on `3500579`; the Release workflow and the CI of the tag were green, the CI of `main` had one unstable UI test (`RulesViewModelTests.Edited_Rule_RoundTrips…`) that passed on the re-run (cause not known, listed for 1.4.3). `Baton.exe` and `batonctl.exe` from CI are byte for byte the local build; release key signatures verified with `tools/verify-release.ps1` on `Baton.exe`, `batonctl.exe`, the installer and the extension package, and `SHA256SUMS.txt` matches (it has CRLF line endings, so `sha256sum -c` needs them stripped: 1.4.3). 17 files attached, as for 1.4.1; no Authenticode signature. "Check now" from a 1.4.1 portable copy offers 1.4.2 and installs it, with `batonctl.exe` and the extension following. Scoop bucket updated (1.4.2), no winget. The installed app was updated with the CI installer: 50 downloads before and after, schema 10, native host and `baton:` point at the installed program, no new entry in Run; the installer moved Baton's own entry to the end of the user PATH (same entries). Graph updated.
- The CI of `main` failed twice on `RulesViewModelTests.Edited_Rule_RoundTrips…`: the test writes "1,5" and the rules window reads numbers with the thread's culture, which in `Baton.UiTests` is the machine's (English on the CI) unless an earlier test applied Italian. The test now sets `it-IT` itself (`tests/Baton.UiTests/TestCulture.cs`, restored afterwards); red shown with en-US, then green; with a forced English start the whole UI suite passes. ## 2026-11-15
- 1.4.1 fix to step 4: FTP downloads asked for by the local API are now checked again when the connection is made, not only when they are added. Baton resolves the name itself and connects to the address it checked (plain FTP), or checks the remote address during the TLS handshake and after it (FTPS); the data connection is always passive and goes to the control connection's address, so the address a server announces in PASV is ignored (`src/Baton.Core/Net/Transports.cs`, `NetworkContext.cs`, tests in `tests/Baton.Tests/FtpPublicOnlyTests.cs`). First text of `docs/API.md`, including why the pipe with `origin=api` needs no token.
- 1.4.1 step 5: rules engine. Conditions in AND (domain with subdomains, address pattern with wildcards or a regular expression run without backtracking, extension, category, size only when known, origin) and actions (folder, category, queue, start now / queued / paused, rename with `{name}{ext}{host}{date}{time}{category}{n}`, scan, connections, user agent, limit for this download, skip the confirmation, show in folder, open when done) in `src/Baton.Core/Rules`, saved in the `rules` table. The rules are evaluated once, when a download is added (`DownloadService.Rules.cs`, next to the duplicate check); the first that matches wins and whatever the entry chose itself stays. The rename works on the name the server reveals and the duplicate check compares that name; the real extension is always kept and a program or script extension is never added. "Open" is refused for programs and scripts and needs a scan that found nothing (it turns the scan on for that download); every refusal and every application goes to the activity log. Schema 10 also gets `downloads.rule_applied`. Tests: `tests/Baton.Tests/RuleTests.cs`.
- 1.4.1 step 6: the Rules window (toolbar button "Rules", also Settings > Automation > Rules): the list in order with an on/off box per rule, reorder with the arrows or Alt+Up/Down, one form for conditions and actions, validation (name, at least one condition, regular expression, full folder path, numbers) and a preview that says which rule, as edited, would apply to an address and what folder and name it would give (`src/Baton.App/ViewModels/RulesViewModel.cs`, `Views/RulesWindow.xaml`). A rule that skips the confirmation lets the browser and clipboard entries add at once. Tests: `tests/Baton.UiTests/RulesViewModelTests.cs`, gallery entry `rules` in both themes and languages.
- 1.4.1 step 7: documentation and version. README.it.md gets the API and rules sections, README.md a short summary, CHANGELOG a 1.4.1 entry (with the known behaviour of updating from 1.3.6), ROADMAP and `docs/API.md` are updated, and the app, `batonctl` and the extension are 1.4.1.
- 1.4.1 step 7b: fixes before the real trials. The queue (and category and folder) the add dialog preselects is no longer an explicit choice, so a rule "site → queue" works from the dialog; the dialog says "Rule: name" and shows the queue and folder the rule gives, and whatever the user changes stands (`AddDownloadViewModel.cs`, tests in `tests/Baton.UiTests/AddDialogRuleTests.cs`). The extension sends the size the browser knows (`totalBytes`, else `fileSize`) as an optional `size`, validated by the app and ignored by older ones, so size conditions work for intercepted downloads (`extension/rules.js`, `background.js`, `BrowserDownload.Size`, `MainViewModel.HandleDownload`). Rules travel with "Export settings…" (categories and queues by name, no ids) and are imported with a preview, duplicate handling and the existing risky-rule switch-off, never ticked in advance (`PortableData.cs`, `PortableImport.cs`, tests in `tests/Baton.Tests/RulePortabilityTests.cs`). The flaky `Control_RemoveAllCompleted…` test waited for `Completed` but "remove all" takes only what `CompletedToClear()` lists (the job leaves the active set a moment later); it now waits for that, and two sibling tests too. `LocalApiTests` picks another port when the one it found free was taken in between by a parallel test class. CHANGELOG notes that "scheduling" in a rule means choosing a scheduled queue.
- 1.4.1 step 8: real trials with an isolated app (`BATON_DATA`), then two fixes found in the screenshots. API: missing or wrong token, wrong Host, Origin header, the 120/minute limit, private addresses (127.0.0.1, localhost, 192.168) refused unless allowed, `file:` and `folder` refused, a body over 1 MB, duplicate, levels read-only / read and add / extended / off, a busy port (the app stays up). Rules from the native host: a size the browser knows fires a size rule, no size or a small one does not, a rename gives `2026-11-15-manual-1.pdf`, "open" is refused for an `.exe` (activity log), a negative size is refused; from the add dialog "Rule: name" is shown and a site rule sets the queue and folder. Fixed: the "Speed limit" label of the rule form was cut (`RuleSpeedLimit` is shorter) and the activity log's action and detail columns were cut without a sign (ellipsis and tooltip, `ActivityLogWindow.xaml`).
- 1.4.1 review fixes (code and security review of the stage). A rule that skips the confirmation now looks at the browser's file name, as the add does; a copied link that is a known duplicate honors "add anyway"; the API's accept loop survives a transient listener error; browser requests (`Sec-Fetch-Site`, also "no-cors" GETs without `Origin`) are refused and only calls with the right token use the 120/minute budget; the activity log keeps no user info even when a password holds `@`, `?` or `#`; "open when done" refuses more types the shell runs, mounts or opens with macros; history pruning tests each drive once (`LocalApiServer.cs`, `AutomationLog.cs`, `ExecutableTypes.cs`, `DownloadStore.History.cs`, `MainViewModel.cs`). Left open: rules whose stored text cannot be read are dropped by the next save; rule regexes are compiled on each match; the activity log's action and outcome words are English.
- Next: release steps (squash, sign, publish, tag) after the go-ahead.

## 2026-11-13
- 1.4.1 in progress, step 0: fixes found by the review of 1.4.0. The "same name" rule is compared with the final name, known once the server has answered, and a name guessed from an address with a query string no longer counts (`DuplicateDetector.CheckFinalName`). - 1.4.1 step 2b: Settings › Automation tab: level of the MCP server and of the local API (off by default), API port (1024-65535), a hidden API token with Show, Copy and New token (the new token is stored at once and the old one stops working; it is created on first save when the API is turned on), "Allow addresses of the local network" and an Activity log button (wired in the next step). Token generation and constant-time matching in `src/Baton.Core/Integration/AutomationToken.cs`; the tab is in `SettingsWindow.xaml` / `SettingsViewModel.cs`, with tests in `tests/Baton.UiTests/AutomationSettingsTabTests.cs` and a gallery entry for the tab.
- 1.4.1 step 3: activity log. `AutomationLog` (`src/Baton.Core/Automation/AutomationLog.cs`, store methods in `DownloadStore.Automation.cs`) keeps 30 days or 10,000 lines, cuts every address before its query, fragment and user info, and is shown in a new window (Settings > Automation > Activity log, filter by origin, Clear). - 1.4.1 step 4: local REST API on `127.0.0.1` (`HttpListener`, `src/Baton.Core/Integration/LocalApiServer.cs`, description in `docs/openapi.json`, served at `/api/v1/openapi.json`). Addresses an agent asks for must be http, https or ftp and not on this computer or a private network unless the setting allows it; the download itself carries `RequestContext.PublicOnly`, so every request and redirect is checked again (`ControlHandler.AddAsync`, `RequestContexts.ApplyTo`). `folder` is refused.
